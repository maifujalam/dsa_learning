================================================================================
 2. PROBLEM FACED
================================================================================

Ping between the two ECS instances (10.0.0.159 <-> 192.168.0.244) was FAILING
with 100% packet loss in BOTH directions, even though the IPsec tunnel appeared
to be established.

  From rahees ECS -> 192.168.0.244 : 4 packets transmitted, 0 received (100% loss)
  From waleed ECS -> 10.0.0.159     : 4 packets transmitted, 0 received (100% loss)

================================================================================
 3. TROUBLESHOOTING STEPS PERFORMED
================================================================================

The connectivity path was verified layer by layer:

STEP 1 - IPsec tunnel status
  Command: aliyun vpc DescribeVpnConnections --profile <p> --VpnConnectionId <vco>
  Result : Master tunnel on BOTH sides = "ipsec_sa_established" (State: active).
           (Slave/DR tunnels showed "ike_sa_not_established" - expected, they are
           standby only.)
  Verdict: Tunnel is UP. Not the problem.

STEP 2 - VPC route tables
  Command: aliyun vpc DescribeRouteEntryList --profile <p> --RouteTableId <vtb>
  Result : rahees : 192.168.0.0/16 -> VpnGateway  (Status: Available)
           waleed : 10.0.0.0/16    -> VpnGateway  (Status: Available)
  Verdict: VPC routes to peer subnet exist and are active. Not the problem.

STEP 3 - Security Group rules (ICMP)
  Command: aliyun ecs DescribeSecurityGroupAttribute --profile <p> \
             --SecurityGroupId <sg> --Direction ingress
  Result : Both security groups ALLOW ICMP -1/-1 from 0.0.0.0/0 (Accept).
  Verdict: Security groups permit ping. Not the problem.

STEP 4 - OS-level firewall + live ping (via ECS Cloud Assistant RunCommand)
  Command: aliyun ecs RunCommand ... (ping + iptables -L + firewalld/ufw status)
  Result : iptables INPUT policy = ACCEPT (no blocking rules);
           firewalld = inactive; ufw = inactive; on BOTH instances.
           Ping still 100% loss both directions.
  Verdict: OS firewall is open. Not the problem.

STEP 5 - VPN GATEWAY destination route table  <-- ROOT CAUSE FOUND HERE
  Command: aliyun vpc DescribeVpnRouteEntries --profile <p> --VpnGatewayId <vpn>
  Result : Custom destination routes = 0  (VpnRouteEntries: EMPTY) on BOTH gateways.
           EnableBgp = True on the gateway, BUT the IPsec connection had
           EnableTunnelsBgp = False, so NO BGP routes were learned either
           (VPN_BGP route count = 0).

================================================================================
 4. ROOT CAUSE
================================================================================

The VPC route entry ("peer CIDR -> VPN Gateway") only delivers the packet TO the
gateway. In Alibaba's dual-tunnel VPN Gateway model, the gateway then needs its
OWN destination route telling it to forward that traffic INTO the IPsec
connection (vco).

That gateway-level route was missing on both sides (custom routes = 0), and BGP
was not active on the tunnels, so the gateway had no next-hop for the peer CIDR.
Packets reached the gateway and were BLACK-HOLED -> 100% loss symmetrically,
despite a healthy IPsec SA.

================================================================================
 5. FIX APPLIED
================================================================================

Added one destination route on each VPN gateway, pointing the peer CIDR into the
IPsec connection (weight 100 = use the active/master tunnel):

  # rahees-uat account
  aliyun vpc CreateVpnRouteEntry --profile rahees-uat --RegionId me-central-1 \
    --VpnGatewayId vpn-l4vmar5jpqtz38bdowvwg \
    --RouteDest 192.168.0.0/16 \
    --NextHop vco-l4vu2jzn2rcz5tv050qrm \
    --Weight 100 --PublishVpc false

  # waleed-uat account
  aliyun vpc CreateVpnRouteEntry --profile waleed-uat --RegionId me-central-1 \
    --VpnGatewayId vpn-l4vy7kihph9spb4epjmo4 \
    --RouteDest 10.0.0.0/16 \
    --NextHop vco-l4vnui2cp5ir7yzt4041r \
    --Weight 100 --PublishVpc false

  (PublishVpc=false was used because the VPC route tables already contained the
   peer routes to the gateway; publishing would have collided with them.)

  To reverse: aliyun vpc DeleteVpnRouteEntry --profile <p> --VpnGatewayId <vpn> \
              --RouteDest <cidr> --NextHop <vco> --Weight 100

================================================================================
 7. NOTES / RECOMMENDATIONS
================================================================================

  - Current setup uses STATIC routing on the gateways (works, no failover).
  - The gateways have EnableBgp=True but the IPsec connection has
    EnableTunnelsBgp=False, so BGP is effectively unused.
  - For automatic failover to the DR/slave tunnel, either:
      (a) enable BGP on the tunnels, or
      (b) add a second gateway route through the DR path with a lower weight.
  - Next possible tests: TCP services (SSH/HTTP) across the tunnel, MTU checks,
    and throughput measurement.
